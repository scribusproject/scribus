# Phase 6: native INDD format probe

This is the first, read-only step toward a separate native INDD importer. It does **not** open or convert an INDD document, recover editable text, or add `.indd` to Scribus's supported-document filters. IDML remains a distinct format and import path.

`scribus/plugins/import/indd/inddprobe.*` reads only the first two 4096-byte header blocks. It checks the INDD signature, `DOCUMENT` type, byte-order marker, nonzero format version, and a database-page count that fits inside the file. The header with the higher sequence number supplies the reported format version and database-page count. A database page is a container block, **not** a document page. The probe never writes to its input.

`scribus/plugins/import/indd/inddmetadata.*` reads the current contiguous-object stream starting at the validated database boundary. It checks each object header/trailer, bounds the scan, and accepts an XMP packet only when its declared length matches the object. XMP packets larger than 16 MiB, malformed XML, DTDs, and entity references are rejected. The read-only result currently exposes title, first creator, created/modified dates, and packet byte count when present. Missing fields stay empty; this is not page-content recovery or a preview renderer.

`scribus/plugins/import/indd/inddpreview.*` extracts saved, page-numbered JPEG thumbnails from that same XMP packet. It accepts only the requested page's `xmp:PageInfo` entry, validates Base64 and JPEG decoding, caps compressed data at 8 MiB and dimensions at 4096 pixels, and returns the JPEG's actual dimensions. In one local sample the XMP declares a 256×256 preview area but the aspect-preserving JPEG is 256×198. No preview is reported when the requested page lacks a saved thumbnail. These thumbnails are not editable page content, and InDesign can save documents without them.

`scribus/plugins/import/indd/inddinspection.*` extracts a bounded XMP preflight inventory: optional `xmpTPg:NPages` (zero means unknown), deduplicated PostScript font names from `xmpTPg:Fonts`, and deduplicated resource URIs from `xmpMM:Ingredients`. Ingredient URIs are historical/reference metadata, **not** verified live links or a missing-link report. The two available samples contain fonts and ingredient references but no `NPages`, so no document page count is claimed. The parser rejects invalid counts, oversized fields, excessive nesting, DTDs, and entities. Synthetic tests include deterministic byte mutations; they are a regression check, not a substitute for coverage-guided fuzzing.

Build and run the synthetic validation suite:

```sh
cmake --build build-qt-6.11.2 --target inddprobetests
ctest --test-dir build-qt-6.11.2 -R '^inddprobetests$' --output-on-failure
```

For local QA only, one or two user-owned INDD paths can be supplied through `SCRIBUS_INDD_TEST_FILE` and `SCRIBUS_INDD_TEST_FILE2` when running that test. No proprietary fixtures are committed or copied into the repository. The two available portfolio samples passed the probe, XMP metadata extraction, saved-preview extraction, and preflight inventory; that result establishes read-only inspection only, not import fidelity. Optional local tests accept absent XMP fields or saved page thumbnails, since these are document-dependent rather than guaranteed INDD features.

A controlled InDesign 2026 experiment used a new one-page document with a single text frame and an IDML export, all stored outside the source tree. The first INDD contained the visible story as a byte sequence in its database region. After replacing that story and saving a second INDD, **both the current and previous story text remained in the binary file**, at distinct offsets. This establishes that scanning for readable strings cannot determine which text is live, let alone recover frame placement, styles, or editability. The experiment is evidence for a structured database parser; it is not a supported format specification or a native import implementation.

The matching InDesign 2026 IDML was used as a separate editability oracle with `scribus/tests/scripts/test_idml_oracle.py`. The one text frame imported, its story matched the exported text, a Scripter edit succeeded, and the edited text survived an SLA save/reopen. The later two-frame export passed the same edit/save/reopen check for both stories. This validates these **IDML** paths only; it does not imply native INDD content was imported. The manual QA script takes `SCRIBUS_IDML_ORACLE_FILE`, `SCRIBUS_TEST_OUTPUT_DIR`, and either `SCRIBUS_IDML_ORACLE_TEXT` for one story or JSON-array `SCRIBUS_IDML_ORACLE_TEXTS` for several; source documents stay outside the repository.

`scribus/plugins/import/indd/inddblockdiff.*` adds a bounded, read-only comparison of physical 4096-byte database blocks in two compatible INDD files. It rejects mismatched format versions or stream byte order, compares the common block prefix when database sizes differ, reports both block counts, and caps scans at 262,144 blocks (1 GiB of common blocks per input). The controlled one-story edit changed 32 of 208 physical blocks. This narrows future record-mapping experiments but does **not** establish which records are live. It compares both header blocks as well as database blocks and deliberately ignores the trailing XMP object stream.

A third, disposable InDesign 2026 fixture added a second text frame to the edited document. Its IDML export contains both visible stories. Its INDD grew from 208 to 211 database blocks; 35 of the 208 common blocks changed. The superseded first-story text visible in the previous save was not found as the same byte string in the new file. This reinforces that neither string presence nor a changed-block list can identify live records. No fixture is copied into the repository.

A fourth fixture changed **only the second frame's horizontal position** by 10 IDML units (`ItemTransform` x translation -6 to 4). Both story strings and the two `ParentStory` mappings stayed unchanged in the IDML export. The native INDD grew from 211 to 212 database blocks; 38 of the 211 common physical blocks changed. The second story's readable bytes moved from database block 86 to block 203, and the first story's bytes shifted within block 202. The optional local C/D comparison passed with `SCRIBUS_INDD_EXPECTED_CHANGED_BLOCKS=38`. Thus even a geometry-only save can relocate readable story data; an offset-based text extractor would be unsound. The bytes immediately before the two current stories contain values three greater than their IDML `Story Self` IDs in these fixtures, but that correlation is **not** a validated native record schema or a reliable live-story discriminator. In particular, the earlier text-only save retained superseded story bytes. No content importer should use this tentative mapping without validated record ownership and liveness.

A fifth disposable fixture appended a marker to the second story without removing its earlier text. The IDML change was confined to that story and the document's save metadata/name. Its INDD grew from 212 to 213 database blocks; 19 of the 212 common blocks changed. The native page containing the edited story retained both the new and previous text in separate length-delimited entries. The earlier entry's two-byte field at offset +2 became zero, while the new entry had a nonzero value. This is evidence of a possible free/retired-entry marker in these saves, **not** proof that the field universally identifies live objects. The apparent story ID relationship and any record-to-frame ownership still require independent validation.

`scribus/plugins/import/indd/inddrecordprobe.*` began as an experimental, bounded, read-only probe for the length-delimited envelope chain on one specified database page. That envelope inspection reports only offsets, lengths, and two opaque header words; it does not classify entries as live or infer object ownership. It rejects unsupported/malformed pages and never registers an importer. Synthetic little- and big-endian tests, malformed-length tests, and deterministic byte mutations passed. Optional local runs parsed the controlled C page 86 (30 envelopes), D page 203 (23), and E page 203 (25); those fixtures remain outside the source tree. Set `SCRIBUS_INDD_RECORD_TEST_FILE`, `SCRIBUS_INDD_RECORD_TEST_PAGE`, and optionally `SCRIBUS_INDD_RECORD_EXPECTED_COUNT` to repeat a local check. A parsed candidate page does not mean the entire INDD database is understood.

The record probe now also offers a document-wide **candidate catalog** with hard caps of 65,536 database blocks (256 MiB) and 100,000 envelope headers. It reads each block once, reports parsed versus skipped pages, and returns only opaque page/offset/length/header references. Before the guarded short-header variant below was added, it parsed 13 candidate pages in each controlled C, D, and E save, containing 261, 259, and 274 envelopes respectively. These counts can be checked locally with `SCRIBUS_INDD_CATALOG_EXPECTED_PAGES` and `SCRIBUS_INDD_CATALOG_EXPECTED_RECORDS`. This is intentionally incomplete coverage, not a document object index. The next prerequisite for native import is locating the active database directory and proving UID-to-record ownership across saves, including retired records. No user-visible INDD content import is enabled.

On a subset of those little-endian candidate pages, the length-delimited chain ends at page offset `0xf5c`. In the controlled B–E saves, a footer entry at `0xf60 + 4 × (31 − slot)` points back to the envelope offset for every ordinary nonzero slot (`1`–`31`) on each such page. For example, the second-story slot `18` points to offset `0x2a0` in D and `0x7c` in E; the retained older E entry has slot zero and is not mapped by this table. The probe now reports whether **all** ordinary slots on a page match this observed layout, and whether a particular envelope is covered by that validated page-local table. It does not apply the rule to big-endian files, pages with other chain endings, zero slots, or special slot values. A mismatch leaves the envelope chain available as a candidate but reports no validated footer index. This is a page-local consistency check only: it does **not** show that the physical page itself is active, or identify an object's story/frame owner. The catalog reports the count of footer-validated candidate pages; optional local assertions use `SCRIBUS_INDD_RECORD_EXPECTED_FOOTER_INDEX=1` and `SCRIBUS_INDD_CATALOG_EXPECTED_FOOTER_PAGES`. Native content import remains disabled until the active database directory and object relationships are independently established.

The next controlled comparison found an additional footer correlation. At offsets `4084` and `4088`, every envelope-candidate page in B–E has the pair `(9, opaque token)`. The type-`9` tokens are unique within each of these four saves. Token `19` is at physical database page `207` in B, `86` in C, and `203` in D and E. This relocation matches the movement of the second story's candidate page from C to D, and shows why physical page numbers are not stable identifiers. The read-only catalog reports all observed type-`9` footer pages and counts token collisions instead of silently treating a duplicate as unique. Synthetic tests cover parsed and unparsed pages, a duplicate token, and conservative refusal to interpret big-endian footers. Optional local checks use `SCRIBUS_INDD_EXPECTED_TYPE9_PAGES`, `SCRIBUS_INDD_EXPECTED_FOOTER_TOKEN`, and `SCRIBUS_INDD_EXPECTED_FOOTER_PAGE`. The token is deliberately opaque: this observation does **not** prove it is a logical page ID, identify the active database root, or establish any record's ownership/liveness. It is not used for importing.

The previously skipped type-`9` page at physical page `14` in each controlled save uses a second, tightly guarded layout. Its first envelope begins at byte `20`, rather than byte `32` or later. A 64-byte first envelope is followed by length-delimited envelopes ending exactly at `0xf9c`; there is no zero-length terminator there. Instead, a 16-slot footer table begins at `0xf9c` and points back to every nonzero slot's envelope. The probe accepts this page only when the chain ends exactly at the table and every occupied slot matches its entry. It does not infer document content from those envelopes.

A later comparison found a candidate physical-page map at database page `9` in all four controlled saves. That page has footer type/token `(5, 10)` and a 988-entry little-endian table beginning at byte `128`. Entry `i` is a physical database page number whose target footer repeats token `i`; zero is an empty entry. The first word of page `9` equals the number of empty entries. All populated entries in B–E are in bounds, point to distinct physical pages, and have matching target-footer tokens: B has 18 entries, C and D 21, and E 22. Entry `19` points to physical page `207` in B, `86` in C, and `203` in D/E, exactly tracking the observed relocation. `inspectCandidatePageDirectory()` now validates this entire mapping read-only, with a 65,536-page input cap, and rejects malformed counts, out-of-range or duplicate targets, and mismatched target tokens. It supports only the observed little-endian page-`9` layout; the synthetic suite also checks conservative rejection of unsupported layouts. Optional local assertions use `SCRIBUS_INDD_DIRECTORY_TEST_FILE`, `SCRIBUS_INDD_DIRECTORY_EXPECTED_ENTRIES`, and `SCRIBUS_INDD_DIRECTORY_EXPECTED_TOKEN19_PAGE`. This is strong evidence of a page directory, but it does not independently establish page `9` as the active root in every INDD version, or prove which records inside referenced pages are live. The map is diagnostic only and does not enable importing.

A user-owned, substantially larger portfolio INDD also passed the page-`9` validator with 208 populated entries, so the observed layout is not confined to the tiny controlled saves. A separate read-only audit now compares all physical type-`9` pages against that validated map. All type-`9` pages in controlled B–E are mapped. In the portfolio sample, 157 type-`9` pages are mapped and 106 are unmapped, with no mismatched mapped-footer tokens. This is useful evidence that a physical scan includes pages outside the candidate directory. The audit reports mapped/unmapped and parsed/unparsed counts; it does **not** call either group live or stale, and does not discard or import either group. Synthetic tests cover both groups and rejection when the map is inconsistent. Optional local checks use `SCRIBUS_INDD_AUDIT_TEST_FILE`, `SCRIBUS_INDD_AUDIT_EXPECTED_MAPPED_TYPE9`, and `SCRIBUS_INDD_AUDIT_EXPECTED_UNMAPPED_TYPE9`. No user-owned fixture is copied into the source tree.

`catalogDirectoryMappedRecordPages()` is a separate, read-only view of envelope candidates on type-`9` pages referenced by the validated page map. The existing physical catalog remains available for comparison, including unmapped pages. The mapped catalog rechecks each target footer after reopening the file, caps output at 100,000 envelopes, and reports mapped pages whose envelope layout is still unsupported instead of silently treating coverage as complete. It neither decodes content nor calls mapped records live. Synthetic tests include an unmapped but parseable page, a mapped unsupported page, record-limit rejection, and invalid-map rejection. Optional local assertions use `SCRIBUS_INDD_MAPPED_CATALOG_TEST_FILE`, `SCRIBUS_INDD_MAPPED_CATALOG_EXPECTED_PAGES`, `SCRIBUS_INDD_MAPPED_CATALOG_EXPECTED_PARSED`, `SCRIBUS_INDD_MAPPED_CATALOG_EXPECTED_UNSUPPORTED`, and `SCRIBUS_INDD_MAPPED_CATALOG_EXPECTED_RECORDS`.

The next parser refinement recognizes little-endian type-`9` pages with 16, 32, 48, or 64 footer slots. The table begins at `4060 − 4 × slot-count`; the envelope chain must end exactly there, and every occupied slot must point back to its envelope offset. The high bit on some slot words is ignored only for this index lookup; its meaning is still unknown. A mismatched pointer, duplicate occupied slot, premature chain ending, or unsupported slot count rejects the page. This validation now parses all **157 mapped type-`9` pages** of the portfolio sample, yielding 1,669 opaque envelopes. Controlled B, D, and E pass with 13/256, 14/275, and 14/290 parsed pages/envelopes respectively. C has 14 mapped type-`9` pages, but one contains only a slot-zero envelope and offers no occupied slot to verify; it remains unsupported, so C reports 13 parsed pages/276 envelopes. This conservative exception is tested. No text or geometry has been imported from these envelopes.

The mapped catalog now exposes a separate diagnostic address for each envelope whose page-local slot back-pointer was validated: `(opaque page-directory token, page-local slot)`, together with its current physical page and envelope offset/length. Slot-zero envelopes and envelopes on pages without a validated index have no such address and are counted separately. In B, C, D, and E the validated-slot counts are 238, 261, 263, and 264; the portfolio sample has 1,573 validated slots and 96 unindexed envelopes across its 1,669 parsed mapped envelopes. An inspection of the reverse direction found table entries with small nonzero values but no matching envelope in all five files. The probe leaves these entries uninterpreted; it does not require every nonzero table value to be an envelope offset. Synthetic tests cover flagged slot words, slot-zero envelopes, opaque table values, unmapped pages, and a corrupt back-pointer. This diagnostic address may help compare controlled saves, but **is not** an object UID, a live-record test, or an importable text/frame reference. Optional local assertions can use `SCRIBUS_INDD_MAPPED_CATALOG_EXPECTED_SLOTS`.

`compareDirectoryMappedRecordSlots()` is the next read-only diagnostic. For compatible format versions and byte orders, it compares raw envelope bytes at common validated `(page token, slot)` addresses, reports addresses seen on only one side, and separately counts common addresses whose physical database page moved. It rechecks each common address against its page footer and slot index after reopening the files; unsupported pages and unindexed envelopes remain explicit coverage gaps. Inputs should be static saved copies: this is not an atomic snapshot and one-sided addresses are not reread after cataloguing. A reused slot can represent a different object, and an identical envelope does not prove a live object or an unchanged rendered page. Controlled B→C yielded 237 common addresses, 16 changed raw envelopes, and 6 relocated physical pages; C→D yielded 250/30/23; D→E yielded 256/23/0. The C save still has one unsupported mapped page. These are diagnostic counts, not editability or layout-fidelity measurements. A self-comparison of the portfolio sample found all 1,573 validated addresses identical. Synthetic tests cover identical bytes, edited bytes, relocation, slot replacement, malformed mapping, incompatible versions, unsupported byte order, and limits. Optional local comparison uses `SCRIBUS_INDD_SLOT_DIFF_FIRST_FILE` and `SCRIBUS_INDD_SLOT_DIFF_SECOND_FILE`, with optional `SCRIBUS_INDD_SLOT_DIFF_EXPECTED_CHANGED` and `SCRIBUS_INDD_SLOT_DIFF_EXPECTED_RELOCATED` assertions. The native importer remains disabled.

The diff now also reports raw envelope length changes and shared prefix/suffix runs **after** the opaque eight-byte envelope prefix. This is a byte-range locator, not a decoded text span. In D→E, 8 of the 23 changed common envelopes changed length. At diagnostic address `(19, 18)`, the envelope grew from 76 to 92 bytes; the matching IDML export's second story grew from 31 to 47 ASCII characters, and the full IDML story bytes are present in that validated envelope in each respective save. E also retains the previous story bytes in a separate slot-zero envelope, which the validated-slot catalog intentionally excludes. This controlled correlation supports further research into story records and retired data, but does **not** prove a general encoding, that every valid slot is live, that slot zero always means retired, or how a story owns its text frame. The test can print this address's byte metrics with `SCRIBUS_INDD_SLOT_DIFF_WATCH_TOKEN=19` and `SCRIBUS_INDD_SLOT_DIFF_WATCH_SLOT=18`; no proprietary fixture is committed.

An additional controlled InDesign 2026 pair tested Telugu. A new one-frame document used Anek Telugu Regular and contained `తెలుగు పరీక్ష మొదటి వాక్యం.`; the second save changed that story to `తెలుగు పరీక్ష మొదటి వాక్యం. రెండో వాక్యం.` while its save name/metadata also changed. Matching IDML exports kept the same story identifier and confirmed 27 then 41 Unicode code points. The native saves expose that story at validated diagnostic address `(18, 18)`, but its full text is **not** a contiguous UTF-8, UTF-16, or UTF-32 byte string. Instead, the observed record has an opaque `0x262` header word, a `0x202` word at byte 12, a one-word flag at byte 20, a bounded encoded-section length at byte 22, and a character count at byte 26. From byte 30, `0x4000 | count` runs contain counted ASCII bytes and `0x8000 | count` runs contain counted little-endian UTF-16 code units. The decoded runs include a terminal carriage return not present in IDML `Content`. The same guarded pattern decodes the controlled Latin D/E story at `(19, 18)`.

`inspectCandidateStoryText()` implements this pattern as a **read-only candidate decoder**. It requires a validated mapped page/slot, checks all internal lengths and run counts, caps output to one 4096-byte envelope, and rejects unsupported run kinds, non-ASCII bytes in one-byte runs, control characters other than tab/newline/carriage return, and surrogate code units. It does not scan arbitrary files for strings, guess frame ownership, omit the terminal carriage return, or enable native import. Synthetic tests cover ASCII and mixed Telugu runs, malformed lengths, invalid run kinds/counts, an unpaired surrogate, unsupported records, unindexed slots, and deterministic mutations. Optional local assertions use `SCRIBUS_INDD_STORY_TEST_FILE`, `SCRIBUS_INDD_STORY_TEST_TOKEN`, `SCRIBUS_INDD_STORY_TEST_SLOT`, and `SCRIBUS_INDD_STORY_EXPECTED_TEXT` (without the final carriage return). The controlled Latin D/E and Telugu A/B text matched their respective IDML exports. Telugu A still has one mapped type-9 page with an unsupported envelope layout, so this one successful story is **not** complete document coverage. The next prerequisite is proving relationships from these candidate story records to specific frames and styles, across more saves and format versions; no source document fixture is committed.

`findCandidateRecordWords()` is a bounded, read-only correlation aid for that prerequisite. It scans only validated mapped envelopes, rechecks each envelope after reopening, excludes the opaque eight-byte header, and reports exact little-endian four-byte matches with their diagnostic token/slot and byte offset. It deliberately scans *all* byte offsets because some observed matches begin at offset `66`; it does not call a match a typed UID or link. The default cap is 4096 matches, and unsupported mapped pages and unindexed envelopes are reported as coverage gaps. Synthetic tests cover header exclusion, unaligned byte matches, unindexed data, bad mapping, and limits. `SCRIBUS_INDD_WORD_TEST_FILE` plus `SCRIBUS_INDD_WORD_TEST_VALUE` enables a local-only match listing; no source fixture is committed.

The IDML exports for controlled C/D/E identify two frames (`ufa`, `u112`) with `ParentStory` `ue8` and `u100`; D moves only the second frame horizontally by 10 IDML units, while E edits only its story. The matching Telugu A/B exports identify frame `uf6` with story `ue4`. Searching the native validated records for the *candidate* story word `0x103` in D finds `(19,18)+16` in the decoded story and `(20,10)+88` in a separate opaque record. Searching for the *candidate* second-frame word `0x115` finds `(19,21)+18/+38` in D, then the same two occurrences plus `(18,14)+100` in E. Telugu A's candidate frame word `0xf9` appears at `(18,2)+118` and `(18,21)+66/+86`, but that save also has one unsupported mapped page. These repeatable byte correlations do **not** establish that the words are stable UID encodings: their locations and record shapes vary across the controlled saves, and no validated frame-to-story reference or geometry field has been identified. A native importer must not use these coincidences to assign editable text to frames. Next, isolate the exact record schema and live-object traversal with more independently varied saves, then validate geometry and styles against IDML; retain safe rejection until all required relationships are proven.

The slot-by-slot diff overstates apparent edits when saving repacks envelopes: C→D changes the only frame transform in IDML, yet many native records move to different diagnostic slots. `compareExactCandidateRecordRelocations()` now compares validated mapped envelopes by **exact bytes after removing only the two-byte page-local slot field**. It limits each input to 10,000 cataloged records, revalidates envelopes when reopening, distinguishes unique matches from duplicate-payload ambiguity, and reports both unmatched sides and unsupported/unindexed coverage. This is a comparison of bytes, not a claim that equal bytes identify the same live object. Synthetic tests cover unchanged addresses, slot moves, physical-page moves, payload edits, duplicate-payload ambiguity, malformed/incompatible inputs, unsupported byte order, and limits. Local-only `SCRIBUS_INDD_EXACT_FIRST_FILE` and `SCRIBUS_INDD_EXACT_SECOND_FILE` print the summary and moved addresses.

On the controlled saves, C→D has 261/263 validated slots, **244 unique exact matches** (25 at different token/slot addresses), 14/16 unmatched, and 3/3 ambiguous duplicate-payload records; C still has one unsupported mapped page. The story-edit D→E pair has 263/264 slots, 238 unique matches (6 address moves), 22/23 unmatched, and 3/3 ambiguous. Telugu A→B has 239/241 slots, 219 unique matches (1 move), 18/20 unmatched, and 2/2 ambiguous; Telugu A has one unsupported mapped page. These counts show why the earlier 30 changed same-address envelopes in C→D cannot all be interpreted as edited objects. No geometry or frame ownership is imported from those records.

A second controlled InDesign 2026 experiment isolated geometry more effectively. Starting from the same two-frame D save, a disposable baseline was saved outside the repository, then three independent Save As copies were made: no edit, second-frame X +10, and second-frame Y +10. The three IDML exports retain the same two `ParentStory` values and story-content hashes. Their second-frame `ItemTransform` translations are `(4, -100.8)`, `(14, -100.8)`, and `(4, -90.8)`; the first frame stays `(-6, -258.6)`. The no-edit copy controls for save-name/metadata and database repacking: baseline→no-edit moved 115 exact-payload addresses, whereas no-edit→X changed just 3 common validated envelopes and no-edit→Y changed 5 plus one new slot. The exact-payload comparison reports 194 unique matches/no moved addresses for no-edit→X and 193 unique matches/one moved address for no-edit→Y. These figures concern the controlled saves only.

In all three new native saves, two validated 952-byte envelopes have the 32-bit pair `(0x151, 48)` at byte offsets `896/900`, followed by six little-endian IEEE-754 doubles at `904..951`. Those six values exactly match the two frames' IDML affine transforms, including the independent +10 X and +10 Y changes; the first frame's values are unchanged. `inspectCandidateAffineTransform()` now exposes **only that observed tail** as a read-only candidate. It requires the validated mapped token/slot, exact envelope length and marker, finite values bounded to ±1e9, and a second footer/slot check after reopening. Synthetic tests cover X/Y changes, unsupported lengths/markers, NaN/oversized values, missing slots, bad mapping, limits, and deterministic byte mutations. Local-only `SCRIBUS_INDD_AFFINE_TEST_FILE`, `SCRIBUS_INDD_AFFINE_TEST_TOKEN`, `SCRIBUS_INDD_AFFINE_TEST_SLOT`, optional expected X/Y, and `SCRIBUS_INDD_AFFINE_EXPECT_UNSUPPORTED=1` verified both frames in each new save. The second-frame candidate at `(19,21)` in earlier D/E also matches `(4,-100.8)`, while the first-frame candidate in C/D/E and the one-frame Telugu A save have a different 952-byte tail and are intentionally `UnsupportedRecord`. The decoder is **not** a general INDD geometry parser. The matching values still do not prove that these records are live, uniquely owned by the IDML frames, or linked to the decoded stories. No native import path uses them.

A further disposable InDesign save added a third text frame containing `ThirdFrameProbe2026 omega kappa.`. Its IDML export confirms three distinct `TextFrame`/`ParentStory` pairs, with the original two unchanged. This save exposed a critical directory limitation: physical database page 9 still has a self-consistent type-5 directory (token 10), but it maps token 18 to old physical page 31. A second type-5 directory appears at physical page 10 (token 9) and maps token 18 to physical page 210, which contains the new story bytes and frame candidate. The observed page-9 mapping therefore cannot be treated as a proven active root. An interim fail-closed guard rejected all multi-directory saves until the header-to-directory chain could be investigated; no native INDD import was enabled.

The next controlled step traced a *candidate* chain. In the newer of the two INDD headers, the little-endian word at byte 936 is 7 in a compact Save As copy, 8 after one incremental save, and 7 after the next. Those physical pages have observed type-4 footers and their word at byte 128 points respectively to physical page 9, 10, and 9; those pages have type-5 footers. The selected directory points to the physical type-9 page containing the third-story bytes from the respective save. `inspectCandidateDirectoryRoot()` reports this chain only when the header, 7/8 root page, 9/10 directory page, and observed footer pairs all match. It refuses other layouts. Synthetic tests cover both branches and corrupted references; optional local checks use `SCRIBUS_INDD_ROOT_TEST_FILE` and `SCRIBUS_INDD_ROOT_EXPECTED_DIRECTORY_PAGE`. This is strong controlled correlation, **not** a general INDD root specification or independent proof of record liveness.

`inspectCandidatePageDirectory()` now validates the table on the root-selected directory page instead of always using page 9. It checks the bounded table count, physical-page range and uniqueness, and each referenced page's footer token. It rechecks the root choice after the table walk. The read-only mapped catalog therefore ignores an unselected older directory and admits the controlled three-frame incremental save: directory page 10 is selected, its 18 table entries validate, and the new story at diagnostic address `(18,21)` decodes to the same text as the IDML export (plus the native terminal carriage return). A subsequent incremental save selects page 9 again. Synthetic tests ensure a corrupt selected table or broken root link fails rather than falling back to a valid older directory; an extra unselected type-5 page is not itself an error. Optional local checks use `SCRIBUS_INDD_DIRECTORY_TEST_FILE`, `SCRIBUS_INDD_DIRECTORY_EXPECTED_PAGE`, and `SCRIBUS_INDD_MAPPED_CATALOG_TEST_FILE`. This only improves the research catalog: object liveness, story-to-frame ownership, alternate file layouts, and general import fidelity remain unproven, so no native INDD importer is registered.

`catalogCandidateFrameStoryReferences()` adds a bounded, read-only correlation probe for two observed 124-byte indexed-envelope shapes (`0x2ab` outer / `0x2ad` nested, and the reverse order). It requires their fixed nested markers, lengths, repeated story word, and repeated frame-offset words; it reports the raw frame and story candidate words with their diagnostic token/slot addresses, plus rejected shapes and unsupported/unindexed coverage. It never subtracts an ID offset, calls the words typed UIDs, or assigns text to a frame. In controlled IDML exports, the reported frame word is three greater than `TextFrame Self`, while the story word equals `ParentStory`. The no-edit two-frame save reports `fd/e8` and `115/100`; the incremental three-frame save reports `fd/e8` and `12d/118` **but misses the still-visible second frame**; a later save reports all three pairs. The earlier two-frame D save likewise reports only one candidate pair, despite two visible frames. Thus this shape is repeatable but not a complete relationship traversal, and its presence does not establish liveness. Synthetic tests cover both variants, repeated-word mismatches, nested-marker rejection, unrelated record kinds, invalid mappings, and limits. Optional local QA uses `SCRIBUS_INDD_PAIR_TEST_FILE` and `SCRIBUS_INDD_PAIR_EXPECTED_COUNT`. The next prerequisite is explaining the missing pairs and proving live-object traversal across saves before any native INDD text placement.

The next coverage check found that some root-selected indexed type-`9` pages start with an envelope at byte `0`, not a first-envelope offset word. Their first envelope has page-local slot `1`, whose footer back-pointer is also `0`. The previous parser skipped that first envelope. The read-only parser now considers this layout only for the observed little-endian indexed pages, with a plausible aligned first length and slot `1`; it still requires the *whole* envelope chain to terminate exactly at the footer table and every occupied slot to point back to its envelope. A malformed candidate is rejected rather than falling back to the offset layout. Synthetic tests cover the four observed footer-table sizes, a bad slot-1 pointer, duplicate slots, and a truncated chain. Local tests on both three-frame saves now find validated `(token 12, slot 1, offset 0)` and `(token 16, slot 1, offset 0)` respectively; `SCRIBUS_INDD_MAPPED_CATALOG_EXPECTED_ZERO_SLOT_TOKEN` can assert this without adding the proprietary samples to the repository. This restores an omitted diagnostic address, but **does not recover the missing second frame/story pair** or establish that any envelope is live. A possible UID-to-address table on mapped type-`6` pages remains an unverified hypothesis, not importer logic.

The exact catalog and cross-save counts recorded earlier in this note were measured before the byte-zero coverage fix. They remain a record of those experiments, not current acceptance totals; recompute them with the updated probe before using them for comparisons.

`findCandidateType6RowTargets()` now checks one more **read-only correlation**. On root-selected, directory-mapped type-`6` pages with a bounded row count, it searches 16-byte rows beginning at byte `8` for an exact caller-supplied raw key. A row is returned only if its fourth word is `1`, its third word names a mapped type-`9` page token, the upper half of its second word names a validated page-local slot, and the lower half of that word plus four, rounded up to a four-byte boundary, equals the envelope length. Similar-looking rows that fail those checks are counted as rejected. The function rechecks the selected directory and source-page footer, caps matches, and reports unsupported type-`6` and type-`9` pages. Synthetic tests cover exact and padded lengths, stale-looking rows, wrong marker/length/token, corrupt target back-pointers, oversized row counts, invalid mapping, and limits. Optional local QA uses `SCRIBUS_INDD_TYPE6_TEST_FILE`, `SCRIBUS_INDD_TYPE6_TEST_KEY`, and expected match count, target token/slot, target kind, and target word-at-12 variables.

In the controlled incremental three-frame save, raw key `0x12d` resolves through a row on type-`6` token `17` to the newly recovered type-`9` address `(12,1)`, a 120-byte envelope; a similar row on another mapped type-`6` page fails validation. In the next save, raw key `0xfd` resolves from source token `18` to `(16,1)`. The earlier two-frame D save maps key `0x115` to `(19,24)`. These 120-byte targets contain the corresponding IDML `TextFrame Self` numeric word at byte `+12` in the inspected saves, but that remains a **cross-format correlation**, not a general UID specification or a frame-to-story edge. The still-visible second frame's 120-byte target is now locatable even where the 124-byte frame/story candidate shape is absent. Its story ownership and record liveness remain unproven; native INDD import stays disabled.

The target-row probe now reopens and revalidates each matched envelope and reports its raw words at `+4` and, when present, `+12`. In both three-frame saves, key `0x115` leads to a 120-byte envelope with word `0x3709` at `+4` and `0x112` at `+12`, matching the second frame's IDML `Self` number in this controlled case. A synthetic test also ensures that a 124-byte frame/story pair on an *unselected* older type-`9` page is never cataloged. The real incremental three-frame file has such a second-frame pair on physical page `200`, but page `200` is absent from its selected directory; the later save selects that page and reports the pair. Scanning every physical page would therefore manufacture a relationship that the current root-selected view does not support. The record shapes and story link still need independent decoding; neither the old-page pair nor row order is a valid ownership fallback.

A wider check of the controlled native saves corrected the initial size rule: many valid target envelopes include zero to three bytes of four-byte alignment beyond the row's lower-length field plus four. In the incremental three-frame save, the row with raw key `0x100` carries length field `174`; `174 + 4 = 178`, rounded up to `180`, which matches its validated type-`9` envelope. Its target has raw kind word `0x28f5`, unlike the frame candidate's `0x3709`. The aligned rule admits this *candidate story-head record* without treating it as text or assigning it to any frame. Rows whose rounded size still disagrees remain rejected. This explains the earlier rejection but does not resolve the missing current frame/story edge or establish liveness.

For a compatible local pair, `SCRIBUS_INDD_EXPECTED_CHANGED_BLOCKS` can make the optional test assert the expected changed-block count. It is not set in CI; the controlled pair is not committed.

Next steps, each with independent review: validate candidate story-to-frame ownership and record liveness across more controlled saves, then decode the required geometry, style, and link records with bounds and mutation tests. Only after a coherent supported subset works should an importer be registered and measured for editability, layout fidelity, linked-image behavior, and safe rejection on real documents. Native INDD cannot be substituted with the existing IDML importer.
